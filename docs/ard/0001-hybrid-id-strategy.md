# 0001. Hybrid ID strategy

- Status: Accepted
- Date: 2026-11-13

## Context
Every table needs an ID for joins and foreign keys and some of those IDs will also appear in public API URLs and responses. Titles, seasons, episodes, assets and (later) users will be exposed to clients. Availability windows and join tables are only used inside the server and never appear in the API.

## Options considered
Auto-increment integers, UUIDv4, UUIDv7 and a hybrid.

1. Auto-increment integers (1, 2, 3, ...): The database gives the next number on each insert.
    Gains: Small (4–8 bytes). Easy to index because new IDs always go to the end. Easy to read while debugging.
    Costs: Anyone can guess them. People can sign up and get user ID 100, sign up again a month later and get 200 and guess that 100 users joined in that month. If an endpoint is missing an authorization check, guessable IDs make it easy to read other people's data.
2. UUIDv4 (random): A 128-bit random value like 3f2a9c1e-...
    Gains: Impossible to guess, reveals nothing and doesn't need the database to generate it.
    Costs: Bigger (16 bytes) and unreadable while debugging. Since new IDs are random, inserts land in random spots in the index. This makes the index bigger and slower at large scale.
3. UUIDv7 (time-ordered): It starts with a timestamp and ends with random bits.
    Gains: Also unguessable but new IDs sort after old ones, so inserts go to the end of the index like integers do.
    Costs: Still 16 bytes and unreadable. Anyone holding the ID can read when the row was created. It's also newer: Postgres only generates it natively from version 18. Older versions need an extension or generating it in the app.
4. Hybrid (internal integer + public ID): Every exposed table has two IDs: an integer used internally for joins and foreign keys and a UUID or slug that's the only one the API shows.
    Gains: Fast, compact integers inside the database and safe opaque IDs outside it. The best of both.
    Costs: Two IDs per row, an extra unique index and a rule we must always follow: the internal integer never appears in an API response. One careless response can leak it.

## Decision
We are choosing the hybrid because it's the best of both worlds: integers where speed and size matter, unguessable IDs where clients can see them. Internal IDs will be auto-increment integers. Public IDs will be UUIDv7, generated by Postgres and only tables exposed through the API will have one. We chose UUIDv7 over UUIDv4 because its inserts go to the end of the index and revealing creation time is harmless for our data.

## Consequences
- Positive: Joins and foreign keys use small, fast integers and clients only ever see UUIDv7 public IDs.
- Negative: Every exposed table has two IDs (an extra UUIDv7 column) and an extra unique index, which costs some storage and write time.
- Obligation: The internal integer must never appear in an API response. We enforce this by never returning Prisma models from controllers. Every response goes through a response DTO that only includes public fields.
- Note: Anyone holding a public ID can read the timestamp inside the UUIDv7 and know when the row was created. This is acceptable because creation time is not sensitive for our data.
